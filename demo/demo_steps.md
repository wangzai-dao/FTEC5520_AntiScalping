## 1. The seven actions (main line)

Order matters: **success paths first, then failure paths**, because the failure paths need an unused
ticket.

### Action 1 - the organizer creates an event

- **Web:** Events page -> fill name / price / maxSupply / eventTime / walletLimit -> Create.
- **Command-line equivalent:**

```bash
.venv/bin/python -c "
from datetime import datetime, timedelta, timezone
from backend import ticket_api as api
r = api.create_event('Demo Live 2026', 1, 10, datetime.now(timezone.utc)+timedelta(days=10), 2, False, 'organizer')
print(r)"
```

- **Say:** the event and its stock live in `concertEvents(eventId)`; the log is `ConcertEventCreated`.
- **Evidence:** the transaction card at the bottom of the Events page; gas ~168,000.

### Action 2 - buyerA buys ticket #1

- **Web:** Buy Tickets page -> pick the event -> Buy (the page calls `canPurchase` first).
- **Command-line equivalent:**

```bash
.venv/bin/python -c "
from backend import ticket_api as api
r = api.buy_ticket(1, 'buyerA', 1); print(r)
print('ownerOf(1..3) =', [api.get_ticket_owner(i) for i in range(1, 4)])"
```

- **Say:** the ticket is minted inside the purchase; `ownerOf` is the single source of truth, and what
  the page shows is what the chain says.
- **Evidence:** `TicketPurchased` plus two `Transfer` events (the mint).

### Action 3 - buyerA lists at the 120% cap

- **Web:** Resale Market page -> pick your ticket -> enter 1.2 -> List (the page shows the live cap).
- **Command-line equivalent:**

```bash
.venv/bin/python -c "
from backend import ticket_api as api
print('cap =', api.get_max_resale_price(3))
print(api.list_ticket(3, 1.2, 'buyerA'))"
```

- **Say:** the cap comes from `getMaxResalePrice` using time-to-event, not from a constant in the page.
- **Evidence:** `tickets(3).isListed = true`, `listingPrice = 1.2e18`.

### Action 4 - buyerB buys it and ownership changes

- **Web:** Resale Market page -> Buy that listing.
- **Command-line equivalent:**

```bash
.venv/bin/python -c "
from backend import ticket_api as api
print(api.buy_resale(3, 'buyerB'))
t = api.get_ticket(3); print('owner', t['owner'], 'resaleCount', t['resale_count'])"
```

- **Say:** `ownerOf` moves from buyerA to buyerB, `resaleCount` increases by one, and the 5% platform
  fee books 0.06 ETH on a 1.2 ETH sale.
- **Evidence:** `TicketResold`; My Tickets shows "resale 1/3".

### Action 5 - two bypass attempts are rejected (the key moment)

**5a over-priced listing** -> expect `Price exceeds dynamic limit`

```bash
.venv/bin/python -c "
from backend import ticket_api as api
print(api.list_ticket(3, 3.0, 'buyerB'))"      # 3.0 ETH, far above the 1.2 ETH cap
```

**5b direct transfer** -> the transaction is mined with `status=0` (the contract overrides
`transferFrom` to revert)

```bash
.venv/bin/python -c "
from eth_account import Account
from backend import ticket_api as api
ch = api.chain(); w3 = ch.w3; c = ch.require_contract()
frm = api.get_accounts()['buyerB']; to = api.get_accounts()['attacker']
fn = c.functions['transferFrom(address,address,uint256)'](frm, to, 3)
tx = fn.build_transaction({'from': frm, 'nonce': w3.eth.get_transaction_count(frm, 'pending'),
                           'chainId': ch.settings.chain_id, 'gas': 150000, **ch._fee_fields()})
tx.pop('from')
s = Account.sign_transaction(tx, ch.settings.key('buyerB'))
h = w3.eth.send_raw_transaction(getattr(s, 'raw_transaction', s.rawTransaction))
r = w3.eth.wait_for_transaction_receipt(h)
print('status =', r.status, 'gas =', r.gasUsed, 'tx =', r.transactionHash.hex())
print('ownerOf(3) is still =', api.get_ticket_owner(3))"
```

- **Say:** if the rules lived in the page, both attempts would succeed. They fail, so the rejection
  comes from the EVM - and **gas is charged anyway** (a status=0 transaction is still mined).
- **Evidence:** the `status = 0` line and the unchanged `ownerOf(3)`.

### Action 6 - buyerB shows the QR, the verifier checks in

- **Web:** My Tickets -> generate the QR (payload with tokenId / holder / nonce / expiry / EIP-191
  signature) -> Staff Check-in -> paste the payload -> five checks run -> Check in.
- **Command-line equivalent:**

```bash
.venv/bin/python -c "
from backend import ticket_api as api
from app import qr_utils
tok = 3
p = qr_utils.create_ticket_qr(tok, api.get_accounts()['buyerB'], api.signing_key('buyerB'))
v = qr_utils.verify_payload(p, api.get_ticket(tok))
print('five checks:', [(c['check'], c['ok']) for c in v['checks']])
print(api.check_in(tok, 'verifier'))
print('used =', api.get_ticket(tok)['used'])"
```

- **Say:** the off-chain part proves who holds the ticket; the on-chain part performs the irreversible
  check-in. That is the right split between chain and off-chain.

### Action 7 - the second check-in is rejected

```bash
.venv/bin/python -c "
from backend import ticket_api as api
print(api.check_in(3, 'verifier'))"      # expect: Ticket already used
```

- **Say:** `used` is on-chain state, so a second check-in of the same ticket always reverts, whoever
  calls it.

## 2. Three extra negative demos (20 seconds each)

| Scenario | Command | Expected revert |
|---|---|---|
| Exceed the wallet limit | `api.buy_ticket(1, 'buyerA', 2)` | `Wallet limit exceeded` |
| Buy after sell-out | `api.buy_ticket(4, 'buyerB', 1)` | `Not enough tickets` |
| Unauthorised check-in | `api.check_in(4, 'attacker')` | `Not an authorized verifier` |
| Non-whitelisted presale purchase | `api.buy_ticket(3, 'attacker', 1)` | `Wallet is not whitelisted` |
| Fourth listing (token 2 already resold 3x) | `api.list_ticket(2, 1.1, 'buyerB')` | `Max resale limit reached` |
| Re-list a used ticket | `api.list_ticket(1, 0.9, 'buyerA')` | `Ticket already used` |

> Each of these has a PASS row in `results/test_results.csv`, so an examiner can check the evidence.

## 3. Fallback if the demo fails

| Failure | What to do live | Fallback evidence |
|---|---|---|
| Node down or stuck | switch to screenshots and tables, do not debug on stage | `results/screenshots/01...06.png` |
| Transaction pending forever | move on and present the evidence table | `results/demo_report.md` (27 rows) |
| Page says "contract not deployed" | present chain data only, leave the UI | `results/test_evidence.json` |
| Browser or network problem | run the command-line equivalents from section 1 | terminal output plus hashes |

**Three numbers you can present offline:** 48 cases, PASS 46 / FAIL 0 / 2 deviations, and 24 real
status=0 transactions.
